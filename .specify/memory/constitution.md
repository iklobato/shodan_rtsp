# shodan_rtsp Constitution

## Core Principles

### I. Python SOLID (NON-NEGOTIABLE)
Governed by `~/.claude/code-imutatble-rules.md`. Every function lives in a class;
`__init__` only assigns; collaborators injected; at most 3 params; methods at most
20 lines; no `elif`; one type per variable; Enum over string flags; own exception
types; default private. The `immutable-rules-check.py` hook blocks any new
violation against HEAD. Beats code-quality and ponytail on conflict.

### II. Test-First, tests that can fail (NON-NEGOTIABLE)
Governed by `~/.claude/imutable-tests.md`. A test must be able to fail; no
asserting only that a mock was called; Fakes not Mocks for IO; test the failure
path and the full error; regression test written BEFORE the fix; never test a
private `_` method or framework code; one test, one reason to fail; deterministic
and isolated. Ponytail still decides HOW MANY tests.

### III. Review order and form
Governed by `~/.claude/imutable-review.md`. Read the whole change first. Order:
correctness, then security, then reliability, then readability, then style. Every
finding carries line, why, and fix, prefixed `[blocking]` / `[nit]` /
`[question]`. Critique the code, not the author.

### IV. System-design restraint
Governed by `~/.claude/imutable-system-design.md`. New infra (service, broker,
read DB, CQRS, queue) only with a concrete, written reason. Smallest architecture
that solves the tracked problem. Beats ponytail and framework skills on
architecture conflicts.

### V. Data, API and dependency safety
Database (`~/.claude/imutable-database.md`): bound params never string-built SQL,
no N+1, atomic writes in one transaction, no network call inside a transaction,
live-safe migrations with rollback. HTTP API (`~/.claude/imutable-api-design.md`):
plural nouns, right method, status code that states the result, error and list
shape on NEW endpoints only, `Idempotency-Key` only where a retry duplicates
something serious. Lockfiles (`~/.claude/imutable-dependencies.md`): never
hand-edited, only generated by the tool of the repo, lock and manifest in the
same commit.

## Additional Constraints

- **YAGNI / smallest diff** (ponytail): ship the smallest change that solves the
  tracked problem. Mark a deliberate corner cut with a `ponytail:` comment naming
  the ceiling and the upgrade path.
- **Scope manifest**: every change opens with a one-line IN/OUT scope; every edit
  traces to it; no drive-by refactors, renames, or reformatting of untouched code.
- **No new dependency, framework, or build tooling without an explicit decision.**
- **Never hardcode secrets**; never commit `.env`, keys, or tokens.
- The non-negotiable carve-out holds over every tier: "shorter" never justifies
  skipping input validation at trust boundaries, error handling that prevents
  data loss, security, accessibility basics, or a test of non-trivial logic.

### Project constraints (shodan_rtsp)

- **Authorized targets only.** The tool probes cameras, reads frames and stores
  biometric embeddings. It is used against the operator lab and against targets
  with written authorization. Decision D1 of
  `docs/decisions/2026-11-11-shodan-rtsp-prod-ready.md`.
- **No scope gate exists in code (accepted risk).** Decision D6 chose not to
  enforce an allowlist. Nothing in the code stops a wrong `ip_range`. Every
  change that adds a network egress path MUST state, in its scope manifest, which
  target set it can reach. A change that widens reach without saying so is a
  `[blocking]` finding.
- **Read-only proof.** CVE exploitation modules (decision D5) pull at most one
  frame and MUST NOT write to, persist on, or alter the target. A module that
  writes anything to the target is out of scope for this project.
- **Lab-verified, not assumed.** Decision D24: a front is done only with a test
  that fails if the logic breaks, plus a real run in the lab with the raw output
  pasted. An unmeasured value (for example the face match threshold, decision
  D16) MUST be labelled a placeholder wherever it appears.
- **Retention is unlimited by decision (accepted risk).** Decisions D10 and D13
  keep frames and embeddings forever. Any code that deletes stored frames or
  embeddings contradicts a recorded decision and MUST raise it rather than act.
- **Toolchain**: dependencies and commands come from `uv` and `pyproject.toml`.
  Gates are `uv run pytest -q` and `uv run ruff check .`. There is no CI by
  decision D20, so these two commands are run by hand before every commit.

## Development Workflow

- Tier chosen by the `spec-driven` skill: Low (just do it) / Medium (lightweight
  plan) / High (this spec-kit flow). This constitution binds the High tier; its
  principles still hold at Low and Medium, they are just not ceremonially gated.
- This batch is one High-tier spec, with the five fronts of decision D12 as task
  phases, delivered as one PR per front (decision D32).
- Quality gates before "done": repo formatter, linter, typechecker and tests all
  pass, and what they flag is fixed. "Done" means verified, reviewed, merged,
  running in production; say which of the four is missing otherwise.
- Verify, do not claim: no "works" without a run; state plainly what was not
  checked.

## Governance

This constitution supersedes project convenience on the points it names. When two
rules or modes collide, `~/.claude/rules/precedence.md` decides (immutable rules
over code-quality and ponytail, system design over ponytail, test rules, review
rules, database rules, dependency rules, API rules). The home rule files under
`~/.claude/` remain the single source of truth; amend a principle by editing its
home file, then re-ratify here. All specs, plans and reviews in `.specify/` must
verify compliance; unjustified complexity is a blocking finding.
